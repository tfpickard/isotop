# isotop: eighteen new views

## Objective

Add eighteen views to isotop, each a real simulation driven by real measurements of the
machine, each modelled on a physical, biological or historical system. In build order:

1. `ptolemy`: a geocentric cosmos with Fourier epicycles
2. `mold`: a Physarum slime mold network
3. `chamber`: a bubble chamber event display
4. `horizon`: the OOM killer as a Schwarzschild black hole
5. `hr`: a Hertzsprung-Russell sky
6. `necropolis`: a graveyard of exited processes
7. `hive`: memory as honeycomb
8. `anthill`: syscalls as foraging ants
9. `switchboard`: interrupts as a 1940s telephone exchange
10. `plumbing`: Unix pipes as literal pipes
11. `morph`: Turing patterns
12. `murmuration`: threads as starlings
13. `cortex`: processes as spiking neurons
14. `ouija`: the journal, spelled by planchette
15. `arbor`: the process tree as a tree
16. `canyon`: the geology of uptime
17. `die`: the CPU die in infrared
18. `tesseract`: worldlines in a tesseract whose fourth axis is time

These come next, ahead of any view from the earlier brief (`isotop-brief.md`) that hasn't
been started. Work already in progress finishes first.

## The realness contract

This is the one hard requirement, and it outranks aesthetics:

- Every visual element maps to a measured quantity, or the README marks it as decorative.
- Each view's README section opens with a mapping table: visual element, measured source,
  transform (log, sqrt, smoothing constant, quantum).
- The status legend line names the main mappings, like the existing views.
- `--demo` synthesizes every field a view consumes, so screenshots work on any machine and
  `--time` makes them repeatable.
- When a source is unreadable (permissions, kernel version, hardware), the view degrades
  visibly and says so in the status strip. Live mode never fills a gap with invented numbers.
- Simulations advance on wall-clock `dt`, not per frame. All randomness is seeded from
  process identity and `--time`.
- isotop never escalates privilege. Sources that need CAP_NET_ADMIN or root are optional. The
  README documents `sudo setcap cap_net_admin+ep ./target/release/isotop` as the user's
  choice, and the status strip says which sources are active.

## Context

- Read `AGENTS.md` first. Its pipeline, invariants, gates, conventions and git workflow all
  apply and are not repeated here. Key points: CPU and GPU rasterizers draw identical frames,
  layouts are stable, nothing slower than a stat read runs on the frame loop, process text is
  untrusted and sanitized, no network access, and every `unsafe` block has a soundness comment.
- As of `927b487` on `main`, views are hand-wired through the `View` enum in `render.rs`.
  Newer views live in their own modules (`cells.rs`, `cores.rs`, `strata.rs`, `globe.rs`,
  `reef.rs`, `matrix.rs`). Continue that: one module per view.
- `medium.rs` is the model for simulation state (pure state, no drawing). `strata.rs` already
  records CPU history in every view. `net.rs` already gets `tcp_info` (rtt, bytes_acked,
  bytes_received) for established TCP, while socket links in `Snapshot.links` are socket
  counts only. `journal.rs` reads `journalctl --output=export` with a fixed field list.
- Use a subagent for any repo-wide exploration (for example, mapping how views are dispatched
  through `render.rs`) so the exploration does not fill the main context.

## Prerequisites from the earlier brief

If these have not landed, do them first, one PR each, as that brief specifies:

- **View registry**: adding a view is one module plus one table entry.
- **View picker**: `v` opens a filterable list. Tab cycles a playlist. `--views a,b,c`.
- **Field primitive**: a grid of colours, optionally with heights for lit heightfields, drawn
  as a world-space quad with bilinear sampling, identical in both rasterizers. Picking goes
  through an owner grid that names the process owning each cell. Grid simulations must not be
  drawn as a triangle pair per cell.
- **Simulation utilities**: a uniform-grid spatial hash, an in-tree radix-2 complex FFT, and
  a deterministic per-identity RNG.
- **Model additions**: utime/stime split; nice, priority and policy; `/proc/<pid>/io` split;
  major faults; context switches; start time.

## How to work

- One view or building block per branch and PR, per `AGENTS.md`. Reference the view's issue if
  one exists from the earlier brief's Phase 0, and update its body from this brief. Otherwise
  file one first with `gh issue create`.
- Start every item in plan mode: explore, propose a short plan (data, simulation, rendering,
  layout and degradation), and wait for approval. After opening a PR, stop and report. Do not
  start the next item without a go.
- Each "What you see" below is the target look. Each "Look" line lists references worth
  searching for before planning the visuals.

## The views

### 1. ptolemy

**Mockup:** `docs/mockups/ptolemy.jpg` (still; the animated `docs/mockups/ptolemy.gif` shows the motion if it is in the repo).

![ptolemy mockup](docs/mockups/ptolemy.jpg)

**What you see.** A dark celestial sphere seen from above. At the centre is a small blue-green
Earth: isotop itself, labelled with its own PID, CPU and memory, the observer everything is
measured from. An outer ring of fixed stars (the steady processes) turns once a minute. Inside
it, up to seven planets ride deferent circles, each carrying a chain of thin epicycle circles
spinning on circles like a Fourier drawing machine. Each planet leaves a looping trail, with
the classic retrograde pretzel loops tinted where it runs backward. Spheres are labelled
"Sphere of Mars: compiler-90". The status line reports "compiler-90 is in retrograde".

**Look.** The 18th-century plates of the planets' apparent geocentric paths (James Ferguson,
*Astronomy Explained*). Fourier-series epicycle drawing animations. Apian's *Cosmographia*
sphere diagram.

**Simulation and mapping.**
- Wanderers ("planet" means wanderer) are the seven processes whose state varied most over
  the last minute: variance of `cpu` in cores plus variance of `log2(memory)` in doublings,
  from B1. Hysteresis: a wanderer keeps its sphere until it falls out of the top ten or exits.
  Until 30 samples exist, the status line says the heavens are still forming.
- Spheres are named from the inside out: Moon, Mercury, Venus, Sun, Mars, Jupiter, Saturn,
  assigned by mean CPU (busiest innermost). Reassign only when membership changes. Deferent
  radius is fixed per sphere; the deferent period follows Kepler's T ~ r^(3/2) from that radius.
- Epicycles: z(n) = (cpu(n) - mean) + i (log2 mem(n) - mean), over the 60-sample window, in
  cores and doublings. Use a direct 60-point DFT; it is exact and cheap. Keep the 12 largest
  coefficients, excluding DC. Draw the chain largest-first from the planet's point on its
  deferent; the tip is the planet. The chain replays the last minute as a closed loop once per
  minute, and the README says so. Ease coefficients toward new values across each sample
  interval so the chain never jumps. The scale from units to world space is one global
  constant, soft-clamped with tanh so a wild process cannot swallow the sky; document it.
- Retrograde: the apparent longitude of the planet seen from Earth decreases. Detect it from
  the derivative and tint that stretch of trail. The README explains it as the process's
  swings outrunning its steady revolution.
- Fixed stars: every other process, at stable angles from an identity hash. Brightness follows
  memory on the magnitude scale from `hr`. Births flare as novae; exits fade.

**Data.** B1.

**Tests.** The DFT reconstruction equals the samples at integer times. A synthetic planet whose
epicycle tangential speed exceeds its deferent speed is flagged retrograde, and the converse
is not. Wanderer hysteresis holds under rank shuffles inside the top ten.

### 2. mold

**Mockup:** `docs/mockups/mold.jpg` (still; the animated `docs/mockups/mold.gif` shows the motion if it is in the repo).

![mold mockup](docs/mockups/mold.jpg)

**What you see.** A Petri dish of dark agar with a glowing yellow slime mold. Thick pulsing
veins join busy processes; a fine fractal fringe explores the empty space. Processes are oat
flakes. When a process exits, its flake vanishes and its veins thin and retract over seconds.
A new process is found by the fringe and wired in.

**Look.** Tero et al. 2010, *Science* (Physarum rebuilding the Tokyo rail network). Jeff
Jones's 2010 Physarum figures. Sage Jenson's Physarum work.

**Simulation.** Jones 2010 agent model on a trail grid (start around 384 x 384). Each agent
has a heading and three forward sensors at offset SO and angles +/-SA. It rotates by RA
toward the strongest reading, moves SS, and deposits. The trail diffuses (3 x 3 mean) and
decays. Start from Jones's most-cited setting: SA 22.5 degrees, RA 45 degrees, SO 9 cells,
SS 1 cell, deposit 5, decay 0.1. (SA = RA = 45 degrees contracts the network into minimal
paths; worth trying as an alternative look.) Size the population to the CPU-rasterizer budget, measured. Agents
that wander foodless for too long reappear at food sources, weighted by CPU: the mold
reallocates biomass to food.

**Mapping.**
- Oat flake = process at its stable ground position (reuse the orbit and flow layout). Flake
  area is proportional to memory. Each flake emits attractant in proportion to CPU.
- Socket and pipe links lay a weak scent corridor along the segment between endpoints,
  proportional to measured traffic from B2 (loopback TCP bytes/s, Unix queue bytes) plus the
  socket count. The mold decides whether to use it. The README quotes Tero's result: the
  network that emerges approximates an efficient transport network between the busy
  processes.
- Colour is Physarum yellow on dark agar, tinted faintly near each flake by its kind colour.
- Hover uses the owner grid (nearest flake). A vein on a link corridor names both ends.
- Status: biomass, vein length (cells above threshold), and flakes connected to the main
  network (flood fill).

**Data.** Existing fields plus B2.

**Tests.** The trail decays to zero with no agents and no food. Two strong flakes are joined
by a vein within N steps (fixed seed). An exited flake stops emitting.

### 3. chamber

**Mockup:** `docs/mockups/chamber.jpg` (still; the animated `docs/mockups/chamber.gif` shows the motion if it is in the repo).

![chamber mockup](docs/mockups/chamber.jpg)

**What you see.** A black-and-white bubble chamber photograph that keeps developing: a round
dark window with fiducial crosses and bright thin tracks of bubbles. Busy processes sweep
gentle arcs. Processes winding down curl into tight inward spirals. Small curly delta rays
burst where processes die. Tracks kink, and V-shaped vertices appear from nowhere when
processes fork. Each cycle, a bundle of straight parallel beam tracks enters from the left.
Once a second the chamber expands: a flash, fresh bubbles along the last second of motion,
older tracks fading. Tilting the camera reveals the tracks are helices.

**Look.** CERN bubble chamber photographs (the 2 m chamber, BEBC, Gargamelle). The 1964
Brookhaven Omega-minus discovery photograph. Electron spiral and pair-production photographs.

**Physics and mapping.**
- A uniform field B points out of the screen. A charged track's projected path is a circle of
  Larmor radius r = p_perp / (|q| B) around a guiding centre. **The guiding centre is the
  process's stable home position**, so layouts stay stable and every process gyrates around
  its own place.
- Momentum p_perp is proportional to smoothed CPU. Charge sign: + when user time dominates,
  - when system time dominates (utime/stime split). Below a CPU threshold a process is
  **neutral and leaves no track**, just as neutral particles are invisible in a real chamber.
  The status line counts the neutrals.
- Mass is proportional to memory. Speed along the track is beta = p / sqrt(p^2 + m^2) times a
  visual constant. Bubble density per unit length is proportional to 1/beta^2 (the low-beta
  Bethe-Bloch trend), clamped, so heavy slow processes leave dense tracks.
- Inward spirals are not scripted: as CPU falls, p falls and the radius shrinks.
- Helix pitch: p_parallel is proportional to the memory growth rate (growing rises, shrinking
  sinks). It is visible only with the camera tilted.
- Fork: the child's track starts at the parent's current position. The parent's track kinks.
  If the parent was neutral, the vertex appears from nowhere (a V0). An exec draws a secondary
  vertex marker. An exit ends the track with delta rays, one per thread at death.
- Beam: one straight track per K local timer interrupts per cycle (x86 LOC deltas summed
  over CPUs; on arm64 the timer's IRQ row). Cosmics: one random straight track per K other interrupts.
- Expansion cycle = the sample tick. Bubbles grow over about 200 ms and fade over a few
  seconds. Film grain and fiducial crosses are decorative. A key toggles white-on-black and a
  printed black-on-white.

**Data.** utime/stime, B3, B4.

**Tests.** Larmor radius scales with momentum and charge. Neutral processes leave no track.
Constant CPU keeps the guiding centre at home. A fork creates a vertex at the parent's
position.

### 4. horizon

**Mockup:** `docs/mockups/horizon.jpg` (still; the animated `docs/mockups/horizon.gif` shows the motion if it is in the repo).

![horizon mockup](docs/mockups/horizon.jpg)

**What you see.** A black hole: a round black shadow with a thin bright photon ring. Around it
an accretion disk whose far side is bent up over the top of the shadow and under its bottom,
the classic Luminet and Interstellar look. The approaching side is brighter and bluer, the
receding side dimmer and redder. Processes ride circular orbits in the disk plane: the next
OOM victim on the innermost stable circular orbit, the safest far out. Background stars are
warped and doubled near the hole. When the OOM killer strikes, the victim leaves the ISCO and
spirals in, stretched radially, reddening and dimming. It **freezes and fades at the horizon
instead of crossing**, exactly as a distant observer would see.

**Look.** Jean-Pierre Luminet's 1979 simulated photograph of a black hole with a thin
accretion disk. James, von Tunzelmann, Franklin and Thorne 2015 (*Class. Quantum Grav.*,
Gargantua; theirs is Kerr, ours is Schwarzschild). The EHT M87* image for the ring.

**Physics.** Units with G = c = 1 and mass M setting the scale. Horizon at 2M, photon sphere
at 3M, ISCO at 6M, critical impact parameter b_c = 3 sqrt(3) M (about 5.196M). The camera is
orthographic, so the observer is at infinity looking along the camera direction. Inclination
is the camera tilt: top-down is a face-on disk, low tilt is the dramatic near-edge-on view.

**Rendering: lens vertices, not pixels.** Map every scene vertex (a finely tessellated disk
mesh, process positions, orbit polylines, stars) to its lensed image position, then draw
ordinary triangles and lines. Both rasterizers draw the same lensed geometry, so CPU and GPU
parity and picking come for free.
- For a point at radius r whose direction from the hole makes angle psi with the line of
  sight, the primary image needs a photon sweeping psi. The secondary image needs 2 pi - psi
  and appears on the opposite side of the shadow. The image lies at screen distance b (impact
  parameter) from the shadow centre, along the point's projected direction.
- At startup, trace photons back from the observer for a grid of b using
  d^2u/dphi^2 = 3 M u^2 - u, with u = 1/r. Record the sweep angle at which each radius is
  crossed inbound and, after periapsis, outbound. Invert that table at lookup time.
  Beloborodov's 2002 approximation, 1 - cos(alpha) = (1 - cos(psi))(1 - 2M/r) with
  b = r sin(alpha) / sqrt(1 - 2M/r), is the test oracle for primary images at r >= 6M.
- Draw order: secondary images, then the black shadow disk of radius b_c, then the photon
  ring as a thin ring just outside b_c (drawn, not traced; say so), then primary images and
  processes. Near-side primary images can fall inside b_c; they belong in front of the shadow.
- Disk from 6M to about 30M, with the Page-Thorne flux profile as given in Luminet 1979.
  Observed intensity is proportional to F / (1+z)^4, with
  1 + z = (1 - 3M/r)^(-1/2) (1 + sqrt(M/r^3) b sin(i) sin(alpha_image)) (Luminet 1979). The
  colour temperature T_obs is proportional to F^(1/4) / (1+z), coloured through B5. The sign
  of the Doppler term depends on how alpha is measured: check that the approaching side
  comes out brighter.

**Mapping.**
- Processes take circular orbits ranked by `oom_score` (rank-based, so the kernel's absolute
  scale doesn't matter). Rank 1 sits at the ISCO, with radius growing outward by rank. Ease
  radius changes; never jump. Angular velocity Omega = sqrt(M / r^3) in coordinate time:
  identical to Kepler, and the README should say so.
- `oom_score_adj = -1000` processes orbit far out, labelled unkillable.
- Accretion brightness follows memory pressure (some avg10); full pressure flares the disk.
- OOM kill (a cgroup `memory.events` oom_kill or the `/proc/vmstat` oom_kill counter
  increments, and the highest-ranked process vanished): plunge inside the ISCO with radial
  stretching. The image dims exponentially with an e-folding time of about 4M (map 4M to about
  0.4 s) and never crosses.
- The inspector shows oom_score, oom_score_adj, rank, orbital radius in M, and period.

**Data.** B4 (`oom_kill`), B5, B6.

**Tests.** The table agrees with Beloborodov at r = 10M within tolerance. Secondary images
always have b > b_c. Omega matches Kepler. A plunging image's brightness decays monotonically
and its radius never reaches 2M.

### 5. hr

**Mockup:** `docs/mockups/hr.jpg` (still; the animated `docs/mockups/hr.gif` shows the motion if it is in the repo).

![hr mockup](docs/mockups/hr.jpg)

![hr diagram mode](docs/mockups/hr-diagram.jpg)

**What you see.** **Sky mode:** a planetarium dome of stars in true blackbody colours. Idle
processes glow deep orange-red; busy ones white and blue-white. Each star's size and
brightness follow memory on the astronomical magnitude scale, and its twinkle follows how
erratic its CPU is. Cgroups are constellations: stick figures along socket links, stepped
IAU-style boundaries between them, cgroup names lettered across. Kernel threads have no
memory and so no luminosity; they appear as an unresolved Milky Way band whose brightness is
their count, which is what the Milky Way is. **Diagram mode:** a key sends every star flying
to its place on a Hertzsprung-Russell diagram. Temperature runs on x with hot on the left, as
astronomers draw it; luminosity runs on a log y axis. The machine's own main sequence
emerges, with giants up and right and white dwarfs down and left. Every star is classified,
for example "K3 III" for an idle, huge process or "DA" for a small, busy one.

**Look.** ESO's HR diagram figure. Stellarium with constellation lines and boundaries. Mitchell
Charity's "What colour is a blackbody?" table.

**Mapping.**
- Temperature T = 2,400 K x (1 + cpu/5)^0.47, clamped to 40,000 K, with cpu in percent of one
  core. Idle is about 2,400 K (M), one full core about 10,000 K (A0), twenty cores 40,000 K (O).
- Colour from B5.
- Magnitude m = -2.5 log10(memory / 1 GiB): 1 GiB is magnitude 0, 10 MiB is +5. Star size and
  brightness use a planetarium point-spread scaling.
- Twinkle amplitude = coefficient of variation of CPU over the last 10 s.
- Spectral class from T with the standard boundaries: O >= 30,000; B 10,000; A 7,500;
  F 6,000; G 5,200; K 3,700; M below. The subclass interpolates within the class.
- Luminosity class: fit the machine's own main sequence each sample with a Theil-Sen
  regression of magnitude on log T. Assign the class from the residual in magnitudes: Ia, Ib,
  II, III, IV, V, VI, and D for hot stars well below the fit. Document the thresholds as a
  convention.
- Sky placement: each cgroup gets a stable constellation region on the dome, and stars sit
  inside it by identity hash with relaxation. Boundaries follow a coarse RA/Dec grid, which
  gives the stepped IAU look. Stick figures are socket links inside a constellation; links
  across constellations are faint.
- A birth is a nova. A process with more than 1 GiB that exits goes supernova: a flash and an
  expanding shell.
- The transition between modes takes about 1.5 s. Diagram mode draws axes, spectral-class
  ticks along the top, and the fitted main sequence.

**Data.** B1, B2, B5.

**Tests.** The blackbody table matches known values. Class boundaries. Luminosity classes on a
synthetic population. Layout stability in both modes.

### 6. necropolis

**Mockup:** `docs/mockups/necropolis.jpg` (still; the animated `docs/mockups/necropolis.gif` shows the motion if it is in the repo).

![necropolis mockup](docs/mockups/necropolis.jpg)

**What you see.** A moonlit cemetery fading into fog, rows of headstones receding with the
newest row in front. Headstone height is lifetime CPU time and width is peak memory. Epitaphs
appear on hover. Zombies stand in open graves waiting to be reaped. Services that died
entirely get mausoleums. Small unmarked markers stand for processes that lived and died
between samples. A ghost rises from an old grave when its PID is reused.

**Look.** Caspar David Friedrich, *Abbey among Oak Trees* (1809-10). Highgate Cemetery.

**Mapping.**
- Deaths come from B3. Taskstats gives the full record; the fallbacks degrade as described
  there.
- Headstone height = lifetime CPU time (log). Width = peak RSS (`hiwater_rss`, or the
  observed maximum). Stone tint by kind.
- Epitaph (terminal text, sanitized): name, PID, lifetime, cause. Exit 0 is "exited
  peacefully"; nonzero is "exited N"; a signal is "killed by SIGTERM" and so on. A SIGKILL
  matched to an OOM kill event is "taken by the OOM killer". ACORE is "dumped core". AFORK
  is "forked, never exec'd". Unknown is "died between samples".
- One row per minute of death, newest in front. Children are buried beside parents dying in
  the same minute. More than N deaths from one parent within a second share one mass grave
  labelled with the parent. Cap at about 600 graves; the oldest rows sink into the fog.
- Zombies (state Z) stand in open graves at the front until reaped, then get a headstone.
- When a cgroup's last process exits, its graves gather into a mausoleum named for the unit.
- A ghost rises when a new process reuses a buried PID (distinguished by start time).
- Fog density = memory pressure. **The moon is the real moon:** its phase is computed for the
  current date from the synodic month (29.530588853 days) and the new moon of
  2000-01-06 18:14 UTC.

**Data.** B3, B9 (graves are pickable).

**Tests.** Cause-of-death mapping from codes and flags. Row assignment. Ghost on PID reuse.
The zombie open-grave lifecycle. The cap and fade.

### 7. hive

**Mockup:** `docs/mockups/hive.jpg` (still; the animated `docs/mockups/hive.gif` shows the motion if it is in the repo).

### 11. morph

**Mockup:** `docs/mockups/morph.jpg` (still; the animated `docs/mockups/morph.gif` shows the motion if it is in the repo).

![morph mockup](docs/mockups/morph.jpg)

**What you see.** A glossy embossed dish of Turing patterns seen isometrically. Every process
owns a patch, and its pattern's morphology reads its state. Idle processes are sparse drifting
spots. Light work packs into solitons. Moderate work runs into fingerprint stripes. Busy
processes fold into mazes, then honeycomb holes. Multi-core processes boil in turbulence.
When a process ramps up, its patch visibly grows from spots into stripes and mazes, and calms
back down. A new process nucleates a fresh patch. An exited process stops being fed and its
pattern starves to dark.

**Look.** The Pearson 1993 (*Science*) pattern map. Robert Munafo's xmorphia. Karl Sims's
reaction-diffusion tutorial.

**Simulation.** Gray-Scott: u' = Du lap(u) - u v^2 + F(1 - u) and
v' = Dv lap(v) + u v^2 - (F + k) v, with dt = 1. Use Du = 0.2097 and Dv = 0.105 on a 5-point
stencil, or equivalently 0.699 and 0.35 with Sims's 9-point kernel (0.2 edges, 0.05 corners,
-1 centre). Size the grid and the steps per frame to the frame budget, and measure.

**Mapping (validated in the prototype).**
- Patches form a power diagram of the processes' stable sites, with weights from memory so
  heavier processes claim more dish. The prototype used w = 60 ln(1 + MiB) squared cells on a
  300-cell dish.
- F and k from CPU, interpolated on log(1 + cpu) between these anchors:

  | CPU % | F | k | Look |
  |---|---|---|---|
  | 0 | 0.014 | 0.054 | drifting spots |
  | 8 | 0.030 | 0.062 | solitons |
  | 30 | 0.037 | 0.060 | fingerprint |
  | 80 | 0.029 | 0.057 | maze |
  | 160 | 0.039 | 0.058 | holes |
  | 300 | 0.018 | 0.047 | turbulence |

  Do **not** use the classic "chaos" preset (0.026, 0.051) for the top end: in the prototype
  it settled into a flat, low-contrast fill. (0.018, 0.047) keeps boiling.
- Smooth the F and k maps across patch borders (Gaussian, sigma about 1.5 cells).
- Exit: set F = 0 and k = 0.06 in the patch. It starves within seconds; then hand the patch to
  its neighbours.
- Birth: seed v in the new patch.
- Reseed rule: if a live patch's v maximum falls below 0.05 (a pattern died crossing a dead
  zone of parameter space), reseed a few nuclei.
- Zombies and stopped processes freeze (no update in their patch). D-state desaturates.
- Render v as height in a lit heightfield (field primitive) tinted by kind colour, with faint
  patch borders. The inspector names the Pearson class and the current F and k.

**Data.** Existing fields.

**Tests.** On 128 x 128 for a fixed number of steps, "solitons" produces many small connected
components and "maze" few long ones. Starvation drives v to zero. Reseeding revives a dead
patch.

**Mockup:** `docs/mockups/murmuration.jpg` (still; the animated `docs/mockups/murmuration.gif` shows the motion if it is in the repo).

![murmuration mockup](docs/mockups/murmuration.jpg)

**What you see.** A dusk sky over a dark treeline: thousands of threads flying as one
starling murmuration, a dark, shape-shifting cloud folding into lobes and ribbons. Sheets
seen edge-on show as dark bands. Hovering a process lights its threads in its kind colour
inside the flock. Under memory pressure or an OOM kill, a falcon dives through and a dark
agitation wave ripples across the flock. New threads rise from the roost; exiting threads

**Look.** Starling murmuration photography and video. Ballerini et al. 2008 (*PNAS*,
topological interaction). Hildenbrandt, Carere and Hemelrijk 2010 (StarDisplay). Procaccini
et al. 2011 (propagating waves under predation).

**Simulation (validated in the prototype, 3,750 birds, units per step with dt = 1).**
- Alignment 0.30 toward the weighted mean velocity of the 7 nearest neighbours.
  Same-process neighbours count double, so each process holds together without balling up.
- Cohesion 0.02 toward the centroid of the **21** nearest neighbours.
- Separation 0.4 times the sum of away / d^2 over neighbours closer than 1.5.
- Whole-flock centroid pull 0.0006.
- Roost: horizontal pull 0.004 (r - 80) beyond r = 80, and an altitude band from 35 to 110
  with a 0.01 restoring force.
- Vertical velocity damping 0.10 (birds fly level and turn by banking, which flattens the
  flock into sheets). Noise 0.02.
- Speed 1.0 + 0.3 x busy, from per-thread CPU (B7), so busy threads surge to the front.
- Falcon: flee radius 14, flee acceleration 0.9. Agitation spreads as the neighbours' maximum
  times 0.93 when above 0.35, decays by 0.86 per step, and adds 0.12 jitter.
- Prototype failures not to repeat:
  - A per-process centroid pull of 0.0012 or more splits the flock into separate balls.
  - Cohesion over only the 7 nearest lets closed groups of eight split off as islands.
  - Vertical damping of 0.22 flattens the flock to a pancake that reads as a smear.
- Neighbour queries go through the spatial hash. Cap at 8,000 birds; above that, sample
  threads per process proportionally and say so.

**Render.** Dusk gradient under the existing pressure tint. Birds splat into a density
buffer, alpha = 1 - exp(-1.1 density) with a 2 x 2 splat and a light blur, so dense regions go
black and thin ones grey. Agitated birds weigh 2.6x (banking shows more wing). The orthographic
camera sits at a low elevation (12 to 20 degrees).

**Data.** B7, pressure, OOM events (B4).

**Tests.** With a fixed seed, the largest connected component of the 7-NN graph holds more
than 95% of birds after N steps. Threads sit closer to their own process's threads than to
random ones. Agitation reaches beyond the flee radius.

### 18. tesseract

**Mockup:** `docs/mockups/tesseract.jpg` (still; the animated `docs/mockups/tesseract.gif` shows a
quarter turn in the XW plane, where the tesseract turns inside out and the worldlines lie down
into timelines).

![tesseract mockup](docs/mockups/tesseract.jpg)

**What you see.** A wireframe tesseract in Schlegel projection: an outer cube (now) and an inner
cube (a minute ago), joined at the corners. Each process is a **worldline**, its path through
four dimensions over the last 60 s, with a shaded sphere at its head on the outer cube. Idle
processes run straight in toward the vanishing point. A process using one full core runs exactly
along the light-cone diagonal of an x-w face. Multithreaded processes go superluminal, leave
through the +x cell and glow Cherenkov blue. A `make -j` fans out from its parent's worldline
like a Feynman diagram. The whole thing drifts slowly in the XW plane.

**The core idea: w is time.** The view treats time as the fourth axis literally. It builds a genuine Minkowski diagram from `/proc` with nothing invented.

| Axis | Data | Mapping |
|---|---|---|
| w (ana/kata) | wall-clock time over the last 60 s | -1 is a minute ago, +1 is now |
| x | CPU-seconds used since the window opened (`cpu_time`) | 30 CPU-seconds per edge unit, so x and w share a scale |
| y | resident memory | the same bounded scale the city uses |
| z | seat | grouped by kind, then cgroup, then start time; held for life |

Because x and w share a scale, **the slope of a worldline is its CPU usage**, and c = one
CPU-second per second:
- An idle process is at rest and runs straight along w.
- A process at 100% of one core is lightlike: exactly the diagonal of an x-w face.
- A single-threaded process cannot exceed c. The view doesn't enforce it; `/proc` guarantees
  it, because one thread's CPU time can't grow faster than wall time.
- Only multithreaded processes go superluminal. They leave through the +x cell, compressed
  beyond it, and give off a blue Cherenkov glow at cos(theta) = 1/beta, with beta in cores.
  (Charged tachyons would radiate in a vacuum; that argument is in the literature.)

x at "now" is the process's average utilization over the minute, so heads drift smoothly and
never jitter. z never changes. Nothing is reshuffled.

**Events.**
- Fork: the child's worldline starts on its parent's worldline and curves out to its own seat
  over a couple of seconds (orbit's "fly out of the parent" rule). Fork points are vertices.
- Exit: the usual flash and ring; the dead worldline stays until it slides out the kata side
  60 s later.
- I/O: each sample with disk I/O puts a small cyan glow on the worldline at that moment.
- Socket links: between heads, with the existing link code; `c` still cycles them.

**Projection**, all before the display list exists, so **CPU/GPU parity is free** and nothing
changes in `shaders.wgsl`:
1. Rotate with a 4x4 orthonormal matrix built from plane rotations (XW, YW, ZW, ...), eased the
   same way the camera is.
2. Perspective divide along w (Schlegel), eye at w = 3.5. The largest norm after rotation is
   about 2.2, so the divide never blows up. At rest the present is the outer cube.
3. Hand the 3D point to the existing orthographic camera; rotate, tilt and zoom work unchanged.

Sphere radii scale with the w-perspective factor. Colour from `kind_color`, darkened with
distance in w.

**Frames of reference.** The 4D rotation is camera only. **Boosts** are the physics: a Lorentz
boost in the (w, x) plane changes how the data is described, not how you look at it. That split
keeps the Euclidean rotation and the Minkowski metric from contradicting each other.
- `b` on a selected process boosts into its rest frame: its worldline goes vertical, every other
  tilts, and the "now" cell tilts too, so the present is no longer simultaneous. A superluminal
  process shows "no rest frame" in the status line.
- The guided tour visits processes by boosting into their rest frames, easing the rapidity, not
  beta, because rapidities add.

**Controls.**

| Key | Action |
|---|---|
| `,` / `.` | Quarter turn in the current 4D plane |
| `;` | Cycle the plane: XW, YW, ZW |
| `b` | Boost into the selected process's rest frame; `b` again or Esc returns to the lab frame |
| Home / `r` | Canonical orientation and the lab frame |
| (idle) | Slow drift in the XW plane, about 2 min per turn; any 4D key stops it |

A quarter turn in XW makes time the horizontal axis and CPU the depth along w. The only
orientation in which it looks like a chart is a quarter turn away, and there CPU is the distance
from you along a direction you can't see. The README says exactly that, flatly.

**Invariants.**
- Stable layout: seats held for life; x is a 60 s average; nothing is re-placed.
- Picking: heads are `Sphere` items with identities; worldlines are unpickable `Line`s.
  Selecting a process lights its whole worldline and the fork vertices back to its ancestors.
- Sampling: no new reads. Everything comes from `Snapshot` fields already present: `cpu_time`,
  `memory`, `io_rate`, `kind`, `cgroup`, `parent`.
- History: a `Worldlines` recorder samples in every view, like `Strata::record` (or B1), so the
  tesseract is already a minute deep when opened. Pause and rewind filter the window up to
  `snapshot.elapsed`. Worldlines scroll smoothly between samples.
- Cost: about 1024 processes x 60 samples; straight runs merge into one segment, so an idle
  process costs one line.
- Labels go through the sanitizer; nothing touches the network or needs `unsafe`.

**Defaults for the open decisions** (confirm in the plan before building):
1. No number key (all ten are taken): Tab, the picker, and `--view tesseract`.
2. Drift always on; it's the iconic picture.
3. z is the seat. I/O would mean more but collapse onto one face, since most processes do none
   and many can't be read without root.

**Considered and rejected.** A Q4 hypercube of boolean process states (16 vertices as process
classes, transitions along Gray-code edges): it discards the continuous quantities the view is
built on. A 4D grand tour of four metrics (Asimov 1985): every process moves every sample, which
breaks layout stability.

**Tests** (pure math and state in `src/tesseract.rs`, like `medium.rs`):
`a_process_using_one_core_follows_the_light_cone`,
`single_threaded_processes_never_leave_the_light_cone`, `rotations_preserve_lengths`,
`a_quarter_turn_in_xw_swaps_time_and_cpu`, `boosts_preserve_the_interval`,
`boosting_into_a_process_leaves_it_at_rest`, `no_rest_frame_exists_for_a_superluminal_process`,
`worldlines_keep_their_seat_when_resources_change`, `children_branch_from_their_parent_worldline`,
`exited_processes_keep_their_worldline_until_it_leaves_the_window`. Plus the usual glue (view
registration, status name and legend, draw call, smoke test, README) and a demo that replays a
minute of history, as demo strata does. Estimate 700 to 900 lines, about the size of cells or
globe.

## Constraints and non-goals

- Every `AGENTS.md` invariant, in every PR.
- No new dependencies unless one replaces substantial, error-prone code; propose it in the
  plan and wait. Physarum, Gray-Scott, boids, Izhikevich, erosion, heat diffusion, photon
  tracing, DFT and the Hershey data all stay in-tree.
- Do not change existing views' behaviour or appearance. Strata moving onto B1 must render
  identically; prove it with before and after PNGs.
- Every new text source (paths, IRQ and device names, thread names, taskstats `ac_comm`,
  journal fields) goes through the existing sanitizer.
- Performance: each view holds 10 fps on the CPU rasterizer at 1080p with the demo's 192
  processes, and at least 5 fps at `--processes 1000`. Measure with `--benchmark` and put the
  numbers in the PR. Simulation work counts against the frame budget.
- No privileged operations, ever. The status strip says what's missing and why.
- One item per PR. No starting the next item without a go.

## Done when

For every PR:
- The `AGENTS.md` gates pass in order, including the smoke test, which visits any new view.
- Behaviour tests named as sentences, including the view-specific tests above and layout
  stability (processes keep their places when CPU, memory or population changes).
- CPU and GPU headless renders of the same frame match within the existing parity tolerance;
  attach both PNGs.
- `--demo --view <name> --output` renders a settled, non-empty, repeatable frame with `--time`.
- The README section exists with its mapping table, and everything visible in the view is in
  the table or marked decorative.
- `--benchmark` numbers are in the PR description.
- Tests are never weakened or deleted to make a PR pass.
